Renderer and run

ArticleReference

From SCRAP Wiki, the reference for the SCRAP engine SDK

The entry point, the frame loop, RenderContext, viewports, and DisplaySettings

Renderer and run
CategoryGetting started
Modulewarp_sdk
Sourcewarp_sdk/src/lib.rs
Public items113
Examplecargo run -p warp_sdk --example starter
cargo run -p warp_sdk --example pong

Renderer and run are the entry point of a SCRAP game: Renderer is the trait that a game implements, and run is the function that opens the window and calls it once per frame. Both are re-exported at the root of warp_sdk, with Config, RenderContext, DisplaySettings and SharedGpu. A game is one type that implements Renderer. For a game with title and pause screens, Game shell offers run_shell as an alternative to writing those screens.

Starting a game

fn main() { run::<Game>(Config { window_title: "Game", ..Default::default() }); }

run does a fixed series of steps before the first frame. It sets the application name before any window or GPU work, so that a failure dialog raised during startup can name the product.[1] It installs boot crash reporting, then loads the project's settings. The settings load before the editor link, because the link reports the display settings to the editor as its first message. Then run attaches to an editor if one launched the process. Every application boots through this function, so a project needs no code to be hostable.

Config

Config is Copy, and every string in it is supplied by the application, because the engine must not name any product.[2]

Field Default Meaning
window_mode WindowMode::Windowed(1280, 720) How the primary window opens
window_title "Application" Title of the primary window, also stored as the application name
secondary_window_title "Application — Secondary View" Title of the secondary window, opened on request

The window icon is not a field. More than twenty call sites write Config as a full struct literal, and a winit icon is not Copy, so the icon is a process-wide setting instead. See Application icon.

WindowMode

Variant Behaviour
Windowed(w, h) A window of this many physical pixels, centred on the primary monitor
Maximized Fills the work area. The title bar, the menu bar and the dock stay visible
Fullscreen Takes a space of its own and hides all three

The request for a windowed size goes in as logical units. A physical size at window creation is divided by the scale factor of whichever screen the window server last called main, so a desk with a retina laptop and a 1x monitor would open the same request at two sizes.[3] Runtime changes to the mode, vsync and the frame cap belong to Display mode.

The Renderer trait

Four methods are required. The rest have default bodies, and a game overrides only what it needs.[4]

Required

Method Purpose
new() Construct the game. It takes no arguments and receives no GPU or egui context
input(viewport, input, width, height) Read input for this frame. width and height are the render size
render(viewport, ctx) Record draw calls into the RenderContext. A game usually steps its world here too
gui(viewport, ctx, display) Draw egui in window space. display is a borrow of the global DisplaySettings

Provided: lifecycle

Method Default Purpose
on_close_requested No-op Called once when the process is about to end. This is where a game saves
on_transport_stop No-op Called once on the edge where the editor's transport moves to Stopped

Every quit gesture reaches on_close_requested: the X button, Alt+F4, and the menu or Cmd+Q, which sends no close event to any window. It runs first in the engine's teardown, because the event loop of winit 0.28 ends in process::exit and no destructor runs.[5]

on_transport_stop exists because a host stops a game by no longer calling render, input and game_gui. That suppresses the frame and releases nothing: an audio sink plays on its own thread and keeps playing. A host cannot tear down through hooks that it just stopped calling, so the application gets this edge. It runs before the host clears its running flag.[6]

Frame order

One primary frame on the desktop loop runs in this order:

  1. set_crt_params. The curvature is zero while the CRT is off.
  2. set_mouse_scale.
  3. input.
  4. frame_reset.
  5. render.
  6. Upload of the draw buffers to the GPU.
  7. gui, after the engine style when auto_style is true.
  8. game_gui, in embedded mode only.
  9. scene_underlay.
  10. The scene pass, which loads the underlay and draws the submitted layers over it.[7]
  11. scene_overlay, which therefore inherits the post chain.
  12. The post-process chain and the present.

gui runs after render in the same frame and before the GPU hooks. Both GPU hooks are skipped while a debug buffer channel is active.

The engine paces frames against a budget. The default is about 60 Hz, 16,667 microseconds, and window.frame_cap_hz in the manifest moves it.[8] A hosted game whose panel is not on screen drops to 5 Hz. It is a throttle and not a stop, because the Storyboard reads the last published frame and a resize must still reach the window.[9]

RenderContext

RenderContext collects draw commands during a frame and batches them for GPU submission. It holds CPU-side buffers and touches no device, which is why Smoke test can drive render with no GPU.[10]

View

set_view_pos, set_view_scale and set_view_rotation set the camera. A scale of 1.0 makes the window two units tall. Rotation is in radians, counter-clockwise positive, and zero is north up. set_render_origin sets a floating origin, subtracted from the view position, so that the world-to-screen subtraction in the shaders runs on small numbers. The world-space draw helpers apply it to each position that they store. A caller that emits its own instance positions must subtract the same origin.[11]

Shapes

Call Result
draw_rect(min, max, color) Axis-aligned filled rectangle
draw_rotated_rect(center, half_extent, rotation, color) Rectangle rotated in the vertex shader
draw_line(src, dst, color) Line
draw_circle(position, radius, color) Disc shaded as a sphere
draw_flat_circle(position, radius, color) Disc in the instance colour, flat to the edge
draw_glow_circle(position, radius, color) Disc with a soft edge

draw_circle pushes a texture index that the fragment shader answers with a planet path, so a bullet or a spark comes out as a small ball. draw_flat_circle takes the sentinel that the shader reads as flat, so no normal is built and no light term is added.[12]

Overlay rows

The draw_overlay_* calls draw the same shapes on a higher world-space row. draw_screen_overlay_line, draw_screen_overlay_rect and draw_screen_overlay_circle take normalized screen coordinates, independent of the world camera, and use the size from set_surface_size.[13]

Images

draw_image_simple(position, size, texture_index) draws one sprite at one size. draw_image adds a Vec2 size, a rotation, a tint and flags. draw_mega_atlas_image is the low-level form for the unified mega-atlas system, and draw_scene walks a whole Scene store and pushes one instance per visible object. The render path allocates four mega-atlas slots, and an application decides what fills each one through its atlas set descriptor.[14] set_draw_z sets the depth of later image calls, and the caller must reset it to zero. See Image atlases.

Scene layers

push_scene_layer appends instances to a layer that the application registered. The list holds bytes, because the type belongs to the application. An instance type that does not match the descriptor gives a wrong picture and not a crash, and an unknown index appends nothing.[15] See Render passes.

Game-named calls

A set of verbs, such as draw_planet_circle, comes from Stella Nova. Other verbs of this kind have moved out of the engine, and a new game should not use the remainder.

Counting a frame

drawn_count gives the number of world-space rects, lines, circles and sprites recorded in the frame. frame_fingerprint gives one count per bucket, in a fixed order, with the sum as the last entry. Both exist because the draw buffers are private to the crate. See proving what is drawn.

GPU hooks

scene_underlay and scene_overlay receive a SharedGpu, a live command encoder and the HDR targets. The underlay draws a background, such as a sky, terrain or the fluid surface, and the scene layers draw over it. Lit2d and Fluid kit draw here.

fn scene_underlay(&mut self, shared: &SharedGpu, encoder: &mut wgpu::CommandEncoder,
    hdr: &wgpu::TextureView, _z: &wgpu::TextureView, _cov: &wgpu::TextureView,
    view: &View, _px: [u32; 2]) {
    self.sky.draw(shared, encoder, hdr, view.width(), view.height());
}

surface_px is the window size in physical pixels and not the size of the HDR view. The HDR chain runs at a fixed internal resolution, and the final blit scales it to the window. A pass that needs the target size reads the view.[16] coverage_view is a single-channel shadow target, and a pass that casts no shadow ignores it.

Viewports

ViewportId is a u32, and PRIMARY_VIEWPORT is 0. The secondary window is viewport 1. It runs its own input, frame_reset and render against a separate RenderContext, so render must use its viewport argument when the two views differ.[17] The secondary window opens when the application asks for it.

A second split runs between chrome and the game image. gui lands on the surface in window space. game_gui draws in game-image space onto the LDR image before the CRT pass, so a HUD drawn there carries the same filter as the scene. Two egui contexts are needed, because one context lays out at one screen rect, and a HUD would paint over the toolbar.[18]

DisplaySettings

DisplaySettings holds every post-processing attribute: FXAA, motion blur, depth of field, the bloom and grade values, and the CRT tube. There is one global block for the whole process and not one per window, because a copy per viewport let a second window render the game with different settings and nothing reported the divergence.[19]

DisplaySettings::DEFAULT has every effect off. The bloom and grade sub-switches default to on, under pp_enabled, so a project saved before those switches existed keeps its picture. The struct is serialisable because the game can be a second process and the editor pushes the block to it over a socket. On disk, the table holds only the keys that differ from the default, and copy_crt_tuning_from copies the tuning of the tube as one block.

The display argument of gui is a borrow of the global, taken for the frame.

fn gui(&mut self, _v: ViewportId, _ctx: &egui::Context, display: &mut DisplaySettings) {
    display.crt_enabled = true;
}

The lock is held across the whole of gui, so code inside the frame must not read the global a second time. Re-entering it would deadlock the process with no panic and no log.[20] Post effects is the one-line interface to the same settings, callable from any thread.

SharedGpu

SharedGpu holds every GPU resource that is identical across viewports: the device, the queue, compiled pipelines, atlases and bind group layouts. It is created once at startup, and secondary viewports borrow from it. The device and the queue are Arc-wrapped because the background asset loader shares them. Pipelines and atlases belong to the render thread.[21] Per-viewport state, such as the surface, buffers, post-processing and the view uniform, lives elsewhere. mega_atlas_mapping gives the texture mapping for one slot, and scene_texture_count gives the layer count of the loaded scene textures.

Limitations

  • render receives no delta time, so a game keeps its own clock.
  • set_crt_params carries the horizontal curvature only. A cylindrical tube bows one axis, and the one-scalar hook cannot carry the vertical one.[22]
  • new receives no context, so anything that needs an egui::Context, such as installing fonts, waits for the first gui.
  • The desktop event loop does not call scroll_secondary_camera or pan_secondary_camera.

#pub fn mega_atlas_index(&self, slot: usize, type_id: u32, variant: u32) -> Option<i32>

The global texture index for one atlas entry, or None when the slot does not exist.

This is the neutral resolver under the game-shaped draw_* helpers. It names no game noun: a caller gives a slot, a type id and a variant, and gets back the index draw_mega_atlas_image takes. None says the slot is not there, so the scene loop skips the object and a fixed-slot helper falls back to layer 0. It is pub because a game writing its own draw_resource-style helper resolves through this, not through an engine method that knows the game's nouns.

#pub fn atlas_has(&self, slot: usize, type_id: u32) -> bool

Whether an object's picture is actually registered.

For a panel that has to answer "why is my scene invisible". An unregistered pair does not fail: get_index returns 0, so the object draws SOME texture rather than none, which is worse to diagnose than a blank — it looks like the store put the wrong art on the object.

A slot past the end of the mapping list answers false, which is the case draw_scene skips outright.

#pub fn draw_circle(&mut self, position: Vec2, radius: f32, color: [u8; 4])
#pub fn draw_flat_circle(&mut self, position: Vec2, radius: f32, color: [u8; 4])

A disc in the instance colour, flat from the middle to the edge.

draw_circle pushes texture_index: -1, and the fragment shader answers that with the planet path: it builds a unit-sphere normal out of the fragment position and shades the fill against it. A bullet, a spark and a pickup all come out as little balls, and lighting_wrap only flattens the diffuse half of it — the Blinn lobe stays. This one takes the sentinel the shader reads as FLAT, so no normal is built and no light term is added at all.

True by default. Before gui, the engine installs the editor Style and the zoom keys, so a game that writes no styling draws at the editor sizes and answers Command with +, - and 0. The pixels-per-point lock leaves egui default sizes at half scale on a retina panel, so a bare context looks too small and its zoom keys do nothing; this default answers both.

Return false to keep a raw egui context, or to install a style of your own. A host that runs its own zoom keys, like the shell, returns false so the engine does not step the scale a second time on one press.

#fn game_gui( &mut self, _viewport: ViewportId, _ctx: &egui::Context, _display: &mut crate::types::DisplaySettings, )

The GUI that belongs INSIDE the game image, on a second egui context.

gui above draws in window space and lands on the surface. This one draws in game-image space and lands on the LDR image, before the CRT pass, so a HUD drawn here sits inside the game view panel and carries the same filter the scene does.

Two contexts, because one cannot serve both. A single context lays out at one screen rect, so a chrome panel and a HUD would share coordinates and the HUD would paint over the toolbar.

Called only while embedded mode is on. A host that draws no chrome puts everything in gui and leaves this alone, which is the shipped game.

#fn frame_reset(&mut self, _viewport: ViewportId, ctx: &mut RenderContext)

Reset the draw buffers for a new frame.

Every buffer RenderContext holds is filled by the application, so what a new frame resets is the application's decision. The default clears all of them, which is what every frame loop did by hand.

#fn on_close_requested(&mut self)

Called once, when this process is about to end. Implement to trigger save-and-exit before process termination.

Every quit gesture reaches it — the X button, Alt+F4, and the menu or Cmd+Q, which sends no close event to any window. reclaim is what calls it, and reclaim runs its body once.

#fn on_transport_stop(&mut self)

Called once, on the edge where the transport moves to Stopped.

A host stops the game by no longer calling render, input and game_gui. That suppresses the frame, and it releases nothing: an audio sink plays on its own thread and keeps playing, and every render-side mirror of the dropped world stays in memory. So a host cannot tear down through the hooks it just stopped calling, and the application gets this edge instead.

Called before the host clears its running flag, so the implementation still owns everything it did while playing.

#pub type ViewportId = u32

Unique identifier for a render viewport.

Each viewport corresponds to one OS window with its own wgpu surface, postprocess chain, egui context, and camera state. The simulation thread is shared — all viewports read the same frame's entity data.

Serialisable because the game is a second process now. The Post-processing section edits the copy in the EDITOR, and the picture is composed by the child — so the struct has to cross a socket or the panel writes a global nobody with a framebuffer is reading.

PartialEq for the same reason: the editor sends this on the change and not on the frame, so something has to answer whether it changed. serde(default) is the contract with project_settings. The table on disk holds ONLY the keys that differ from DEFAULT, so every absent field must fall back to it rather than fail the whole block for being incomplete.

#pub const DEFAULT: DisplaySettings = DisplaySettings

What a game gets before it asks for anything, as a const so a static Mutex can hold it.

Default::default() is not callable in a const initializer, and the settings are one global now — so the values live here and Default returns this rather than the other way round.

EVERY EFFECT IS OFF, AND THE VALUES BESIDE THE SWITCHES ARE NOT

A new project draws what it drew: the rects and lines its render method submits, at the colours it chose. It used to draw those through an HDR chain and a barrel-distorted CRT filter, because this const held the look of one game — so the first picture anybody made in this engine came out bloomed, saturated and bent, and nothing in the project said where that came from.

The tuned numbers stay. They are the look those two passes had, and a game that wants it sets pp_enabled and crt_enabled and gets it back whole; a game that wants its own moves the fields beside them. What changed is which of the two states costs a line of code.

AND THE TUBE GREW THIRTY-ONE MORE FIELDS WITHOUT MOVING THE PICTURE

The CRT filter gained a phosphor mask, a parallax model, a per-channel convergence block and a set of visualisation modes. A project that sets only crt_enabled = true today must get exactly the picture it got before them, so every one of those features is off in this const: crt_mask_type 0, crt_mask_strength 0, crt_parallax_strength 0, all six crt_conv_* 0, crt_viz_mode 0, and crt_phosphor_on false. crt_curve_aspect is 1.0, which makes the two-axis barrel equal to the single scalar it replaced.

The fields those switches multiply keep real values rather than zero — crt_mask_triad_px, crt_slot_height_px, crt_eye_dist, crt_glass_ior and crt_mask_boost are divisors, periods or a gain of one, where zero is a divide or a black screen and not a no-op.

crt_phosphor_gui_exempt defaults to 1.0 and is dormant. The default is left where it was because the field is only carried, never read; changing it would rewrite every saved project for no visible effect.
