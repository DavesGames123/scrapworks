Dev console

the Console panel, a mirror of the game's own scrollback

Dev console

The dev console is the channel behind the Console panel, a dock panel that shows the console an application already has and types back into it. The devconsole module of warp_core, re-exported by warp_sdk, is the whole of the part that the engine plays. There is one scrollback with two views: a line printed in the game appears in the panel, and a command entered in the panel runs in the game and prints in both.[1]

Design

The console lives in the application, and the dependency runs one way, so the engine cannot name its commands or interpreter. The application publishes, and the engine draws. Every line that crosses is a string and three bytes of colour.

A snapshot and a revision

The obvious build hooks the function that appends a line, and forwards each line. It fails because a buffer is also cleared, and it drops its oldest lines at a cap. An append-only stream carries neither, so the first cls would leave the panel showing lines that the game no longer has.[2]

So the unit that crosses is a snapshot. The publisher bumps a counter on each change to its buffer, and it republishes when that counter differs from published_revision.

The want clock counts polls

want_console is the same brake as want_census, with one difference. Console output changes only when a command runs, so a publish clock would stand still through each idle frame, and a deadline against a stopped clock never arrives. console_wanted advances the clock instead, so the per-frame question of the publisher is the tick.[3] WANT_GRACE is 3.

Typing is a queue

Running a command needs a renderer, a world, or a mutable borrow of both, and none of these exist when a person presses Return inside a panel draw. The panel records the text, and the application runs it on its own frame. MAX_PENDING is 64.

The panel does not echo what it sends. The console of the application prints the echo, and it arrives with the next publish. A local echo would show each command twice, in this panel only.

Usage

Drain the commands where the game holds what they need, and publish when the buffer changes. Seg is one coloured run, and Line is a row of them.

fn gui(&mut self, _v: ViewportId, ctx: &warp_sdk::egui::Context, _d: &mut DisplaySettings) {
    for cmd in devconsole::take_submissions() {
        if cmd == "reset" {
            self.score = [0, 0];
            self.point();
        }
    }
}

/// Announce the score on the console.
fn point(&mut self) {
    self.rev += 1;
    let line = format!("score  {} : {}", self.score[0], self.score[1]);
    devconsole::publish(
        self.rev,
        vec![devconsole::Line::new(vec![devconsole::Seg::new(line, [200, 200, 200])])],
    );
}

devconsole::publish_words sends the completion vocabulary once, in new. words_published says whether that was done. On the panel side, completions gives the matches for a prefix and common_prefix gives their shared start, and with_console and with_words lend the data for drawing.

API

Side Function Purpose
Panel want_console I am open, or closed
Panel with_console Borrow the lines to draw
Panel submit Queue a command
Publisher console_wanted Is anyone looking; ticks the clock
Publisher publish Install a snapshot
Publisher published_revision Is the snapshot stale
Publisher take_submissions What was typed since the last frame
Publisher has_submissions Peek at the queue

Perf returns its warnings as Line values, because this console is a snapshot that the game owns and the kit cannot add to it.

Across processes

Nothing in this file changed when the editor stopped linking the game. The panel arms want_console and reads with_console in its own copy, and the game polls and publishes in its copy. Host link carries a snapshot up and a want down in pump_console. The cost is a frame of lag.[4]

Reference

This section lists every public item, as the source defines it.

warp_sdk::devconsole

Functions

#pub fn want_console(on: bool)

Panel: I am drawing this. Call it on every frame the panel draws.

false gives up immediately, for a host that knows the panel has gone. Not calling it at all gives up within WANT_GRACE polls, which is the path that actually carries the weight — a torn-off panel whose window was closed never gets to say so.

#pub fn console_wanted() -> bool

Publisher: is it worth comparing revisions at all. Advances the clock.

One relaxed add and one relaxed load per frame when the answer is no, which is the common case and the one that had to be free.

#pub fn publish(rev: u64, lines: Vec<Line>)

Publisher: install a snapshot, and say which revision of yours it is.

rev is the publisher's own counter and is never interpreted here. It is compared for equality and nothing else, so any value that changes on every mutation will do.

#pub fn published_revision() -> u64

The revision of the snapshot now installed, without taking the lock.

A publisher republishes when this differs from the revision it holds.

#pub fn with_console<R>(f: impl FnOnce(&[Line]) -> R) -> Option<R>

Panel: read the scrollback.

A closure rather than a clone, because the panel reads it once per frame and copying the whole buffer to paint the thirty rows that fit is the cost the revision protocol exists to avoid.

#pub fn submit(cmd: impl Into<String>)

Panel: run this on the application's next frame.

Blank lines are dropped here rather than at the far end, so a publisher does not have to guard against a Return pressed at an empty prompt.

#pub fn take_submissions() -> Vec<String>

Publisher: everything typed since the last call, oldest first.

Drains, so a command runs once. Order is kept because console commands are not commutative — cd learn then ls is not ls then cd learn.

#pub fn has_submissions() -> bool

Whether anything is waiting, without draining it.

#pub fn publish_words(words: Vec<String>)

Publisher: these are the words worth completing.

Sent whole and replaced whole. A command table is fixed at build time in most applications, so this is normally called once and never again — but replacing rather than appending means a publisher whose vocabulary DOES change has nothing extra to do.

#pub fn words_published() -> bool

Publisher: have I sent one already.

#pub fn with_words<R>(f: impl FnOnce(&[String]) -> R) -> Option<R>

Panel: borrow the vocabulary to complete against.

#pub fn completions(prefix: &str) -> Vec<String>

The words that extend prefix, in the order the publisher gave them.

Case-sensitive, because a console's commands are. An empty prefix completes to nothing rather than everything: Tab at an empty prompt should do nothing visible, not paste the entire command table into the line.

#pub fn common_prefix(candidates: &[String]) -> String

The longest prefix every candidate shares.

What Tab actually inserts when several words match. Completing to the first candidate instead would pick one of several equally good answers and be wrong most of the time; completing to the shared stem is never wrong, and it is what leaves the caret where a second Tab is useful.

Types

#pub struct Seg
pub text: String,
pub color: [u8; 3],

One run of text in one colour.

Straight RGB, and no style beyond it. A console's own palette is the publisher's business, and a channel that carried bold, italic and a font would be describing a text layout rather than a line of output.

Serialisable because the publisher is now usually in another process and the snapshot travels as JSON. See ToEditor::Console.

Constants

#pub const WANT_GRACE: u64 = 3

How many polls one assertion of interest survives.

Three, not one: the panel and the publisher run on the same thread but in an order neither controls, so a claim made after this frame's poll must still be alive at the next one.

#pub const MAX_PENDING: usize = 64

How many unrun commands are kept.

Bounded because the far side may not be draining: a stopped application runs no frames, and a person can keep pressing Return at a panel that looks alive. The oldest goes, which matches what a queue of intentions should do when it overflows — the newest command is the one still wanted.
