shared state and channels that the engine and the application both read

Types is the types module of warp_core, re-exported by warp_sdk, which holds the shared types and process-global channels that the engine and an application both read. It holds no single concept. The module was one 2700-line file with a dozen unrelated concerns, and it is now a directory with one concern per file, which re-exports all items so that each item keeps its path.[1]

Most of the surface is globals with a small accessor pair. A game normally reaches these through a kit: Display mode uses the display store, and Post effects uses the post store. This article groups the items by concept.

Display settings

DisplaySettings is the one block of attributes for the whole application: the CRT filter, HDR chain, depth of field, FXAA, motion blur and lighting wrap. They describe how the game image looks, and they are not a property of a window. They were once a field on each viewport, so a second window could render the game with different settings and nothing reported the difference.[2] One global replaced them.

Function Purpose
display_settings Read a copy
set_display_settings Replace the block
with_display_settings Borrow mutably for one call
display_is_borrowed Whether a frame holds the borrow
display_section The Project settings section

Renderer::gui receives &mut DisplaySettings, a borrow of this global for the whole GUI frame. The lock is held across the closure, so anything in the frame that takes the global again deadlocks with no panic and no log. The source records that this froze the editor the day that the settings registry was wired in.[3] display_is_borrowed lets such a call fail loudly. It is a flag and not try_lock, because try_lock cannot tell this thread from another thread that holds the lock for a moment.

Every effect is off in DisplaySettings::DEFAULT, and the tuned values beside the switches stay. A new project draws its rects and lines with the colours that it chose, and a game that wants the old look sets pp_enabled and crt_enabled.[4]

Any-thread stores

Two stores let any thread change the frame without touching the lock above. Both are a mutex and a revision that never wait for a frame, and the frame applies the newest value at one fixed point.

The post store is a second copy of the post fields. post_store_get, post_store_update and post_store_revision serve the Post effects kit, and sync_post_store runs in the frame. A post::set applies once, at the next frame. If no update arrived, the global is copied into the store, so post::get shows what the editor and the game wrote. The store does not hold an override that wins each frame, because that would make the Post panel dead.[5]

The display store holds DisplayMode, DisplayWindow and MonitorInfo, with display_store_get, display_store_update, sync_display_store and the monitor functions. Display mode describes these and the frame order. pick_present_mode and frame_cap_budget_us are its pure helpers.

Keyboard channels

RawKey is a physical key as winit reports it. Warp has two paths that bypass egui and the winit input helper.

The raw key ring

egui consumes a key event whenever a TextEdit holds keyboard focus, so a console whose own field has focus goes deaf to the key that closes it. The event loop mirrors each watched press into RAW_KEY_PRESSES from the raw window event, before egui gets it.[6] The watch list bounds the ring, because mirroring all presses would let held keys evict a real press. A full ring of RAW_KEY_RING_LIMIT, 64, drops its oldest entry, so the newest press always lands.

The list is keyed by owner, and the effective watch is the union. watch_raw_keys replaces only the list of its owner, so no registration can delete another subsystem's key. set_raw_key_watch is the RAW_WATCH_APP slot. The owner keying exists because a single list once let one subsystem clear another's keys, and the debug console could not be opened.

take_raw_key removes all pending presses of one key and reports whether any existed, and drain_raw_keys takes them all. push_raw_key and push_raw_key_from are the producers: the first is for a shipped game and the web loop, and the second is for an editor that hosts a game.

Input capture

Keyboard and pointer capture are two independent grabs, and the engine gives neither a meaning.[7]

set_input_capture diverts key transitions into CAPTURED_KEYS in place of the raw ring and egui. pop_captured_key takes them, with true for a press. set_capture_passthrough_keys names the keys that stay global: a console toggle belongs there, because the user must always be able to leave.

The queue carries transitions and not presses, so the two edges of one key live or die together. At CAPTURED_KEY_LIMIT, 64, it drops the oldest press with the release that closes it, and it never drops a release alone. A lost release would leave a key locked on, and the source judges a lost press to be the smaller fault.[8] captured_keys_dropped counts the cost.

set_pointer_capture hides the cursor, warps it to the window centre each frame, and accumulates the drift. take_pointer_delta returns the drift since the last call, and pointer_buttons the held buttons. set_pointer_release_keys names keys that drop the capture. Such a press also reaches the raw ring, so one keystroke can release the pointer and mean something.

Pending flags

PENDING_SCROLL and the PENDING_MOUSE_* flags carry input across event batches between render frames. Without them, scroll would read as 0 on a frame that the render budget skipped.

Transport

PlayState is what the play bar says the simulation should do: Stopped, Playing or Paused. This is deliberately not the pause flag of a game. Game systems write such a flag freely, so a play bar built on one would resume when a story overlay closed. Game code must not clear an editor pause.[9]

Function Purpose
play_state, set_play_state Read and write the transport
play_debug, set_play_debug The debug configuration for the next boot
transport_active, set_transport_active Whether a play bar owns the transport
request_step, take_step_request Run one pass while paused
step_pending Peek at a step, with no consumption
take_play_state_change Report the state once per change

take_step_request has one consumer, the simulation loop. step_pending has no caller today and stays for a reader that has a stake in a step. take_play_state_change exists because a host that wrote its state every frame overwrote what the application did. The first call returns nothing, so a host does not disturb a boot sequence.

The game view

These items carry the scene as a texture in an egui panel. See GameView in gpu. The normal frame draws egui into the LDR image, so the scene is the backdrop of the GUI. In embedded mode, the finished scene is a texture, and a panel draws it.

set_game_view_embedded is a declaration that a host makes once at startup, because it decides whether the chrome is post-processed. It used to be a side effect of a panel draw, so closing a tab could send the whole window through the CRT shader.[10]

GameViewRect is the rect that a panel drew, with the window that it drew in. The window is a field of the rect, because four numbers with no window are numbers that every window believes are its own. The panel publishes the rect each frame, and tick_game_view and mark_game_view_drawn expire it when the panel stops drawing. game_view_remap, game_view_contains and their _in forms map the pointer.

Key routing is separate, because a key has no position. game_view_focused says that the panel holds the keyboard, game_focus_vote and publish_game_focus let each window vote, and game_keys_from combines the two. Outside embedded mode, game_keys_from is true unconditionally, because otherwise a shipped game would be deaf.[11] game_view_host names the window of the panel.

GPU data

These are the plain structs that scene shaders read.

  • View is the view uniform: camera position and scale, star data, time, depth-of-field and lighting values, occluders and the debug mode. The xy field packs the HDR target size into one word, with the width in the low 16 bits and the height in the high 16 bits. This is not the window size. View::width, View::height and View::pack_xy read and write it.[12]
  • Rect is a rect instance, with min, max, colour, rotation and flags. RECT_FLAG_RECEIVE_SHADOW is its one flag.
  • Vertex is a position and colour.
  • Instance holds a position, radius, colour, texture index and rotation.

Windows and viewports

ViewportId is a u32 that names one OS window, with its own surface, post chain, egui context and camera. PRIMARY_VIEWPORT is 0 and always exists. SECONDARY_VIEWPORT_REQUESTED asks for the secondary view, which has id 1.

alloc_viewport_id starts at 2 and never reuses an id. The application allocates the id and then asks for a window, because a dock must fill the new window on the frame of the drop.[13] request_window queues a WindowRequest of open, close, focus or retitle, and drain_window_requests takes the queue once per frame. push_window_closed and push_panel_closed report closures.

WindowGeometry holds the client origin, size and pixels per point of each window. to_desktop, to_local and to_desktop_size convert positions across windows. DragProxyState, set_drag_proxy and drag_proxy carry a drag between windows, and NewWindowPreview previews the window that a drop would open.

FULLSCREEN_TOGGLE_REQUESTED, FULLSCREEN_STATE, WINDOW_MODE_REQUESTED, WINDOW_SIZE_REQ_W and WINDOW_SIZE_REQ_H are the requests that the event loop applies. A game uses Display mode instead.

Instrumentation

RENDER_DRAW_US, RENDER_UPLOAD_US, RENDER_GPU_US and RENDER_FRAME_US hold the phase times of the last frame, in microseconds. GPU_DESCRIPTION holds the adapter and surface as lines of text, and is empty until the device exists. WINDOW_PHYS_W, WINDOW_PHYS_H, WINDOW_SCALE_BITS, SURFACE_W and SURFACE_H hold the sizes of the primary window. An application can read these for a performance report. See Perf and Profiler.

Application identity and previews

app_name returns the product name that run stored with set_app_name, or a neutral placeholder before that. The first call wins. The name is a global because the GPU failure dialog must name the product and cannot take a parameter.[14]

PLANET_PREVIEW_REQUEST, PLANET_PREVIEW_TEXTURE and PlanetPreviewRequest feed the planet preview in GPU module. GUI_ATLAS_TEXTURES holds egui texture ids of atlases for sprites in panels.

Queue one diverted key transition.

── A RELEASE IS NEVER THE ENTRY THAT GOES ───────────────────────────── This queue carries TRANSITIONS, not presses. The consumer reads one edge at a time and holds the key between the two, so the two edges of one key must live or die together.

The queue used to refuse the new entry when it was full. That is the one policy this queue cannot have: with the queue full of presses, every later RELEASE was refused while the presses stayed. The consumer then held keys that nobody was touching, which is the stuck-key fault the pointer and keyboard paths in hostlink/input.rs describe.

Plain drop-oldest is not enough either. A consumer that has already taken a press leaves the matching release at the front, and drop-oldest takes exactly that entry. So the queue drops the oldest PRESS and the release that closes it, in one step, and never a release on its own.

A press is refused only when the queue holds no press to evict. Losing a press loses an action; losing a release locks one on.

#pub fn game_view_rect() -> Option<GameViewRect>

The published rect, copied out — if the panel still draws it. The lock is released before the caller sees the value, so a caller can lock something else without a deadlock.

── A RECT IS ONLY TRUE WHILE THE PANEL IS DRAWING IT ─────────────────── The rect is published as a side effect of playbar::game_view, so it is written only on frames the panel actually draws. Under a fixed layout that was every frame and the static could be read at face value. Under a dock it is not: Code, Strudel and Sauron are tabs of the Game panel's own leaf, so selecting one leaves the panel undrawn — and the last rect standing, naming the very screen area that tab now covers.

What that cost was the POINTER. game_view_contains_in answered true for a point over the Code panel, gui's cursor arbiter read that as "the game owns this pointer" and let the game's CursorIcon::None through, and egui-winit's per-State icon cache meant the chrome never asked for the cursor back. Hovering the Code panel made the mouse vanish.

So a rect expires. One tick of grace, because events for frame N+1 are read BEFORE that frame redraws and republishes: expiring at zero would blank the rect for every event between two frames, which is where the clicks are. Two ticks without a draw is a panel that has stopped.

Clearing at the top of each frame instead would be simpler and wrong: with the panel torn off into its own window, each window walks its own dock, so whichever walked second would wipe a rect the first had just published. A stamp does not care what order the windows draw in.

#pub fn step_pending() -> bool

take_step_request is owned by the sim loop and there can only be one consumer: two swaps against one flag means whichever thread wins runs the pass and the other silently loses the request. So a second reader gets a peek instead.

It exists for a thread that has a stake in a step it does not own. The sim loop owns the consuming take_step_request; two swaps against one flag would mean a step one reader saw was a step the sim never ran, so any other reader gets this peek instead.

NO CALLER TODAY, and the reason is worth recording. The render thread used to read it: an editor pause parked a viewport selection, and the thing that let a parked one land was time moving. The peek is kept because the shape of the problem has not gone away — a step is invisible in play_state, which reports Paused throughout one.

#pub fn take_play_state_change() -> Option<PlayState>

Report the transport state once per change, and nothing in between.

A host that maps the transport onto its own state — a render phase, a camera, a scene — must write that state only when the transport moves. Writing it every frame overwrites whatever the application did in the meantime, and the application then cannot leave the state the host keeps re-asserting.

The first call returns None and records the current state, so a host that starts up does not disturb an application still working through its own boot sequence.

EVERY EFFECT IS OFF, AND THE VALUES BESIDE THE SWITCHES ARE NOT

A new project draws what it drew: the rects and lines its render method submits, at the colours it chose. It used to draw those through an HDR chain and a barrel-distorted CRT filter, because this const held the look of one game — so the first picture anybody made in this engine came out bloomed, saturated and bent, and nothing in the project said where that came from.

The tuned numbers stay. They are the look those two passes had, and a game that wants it sets pp_enabled and crt_enabled and gets it back whole; a game that wants its own moves the fields beside them. What changed is which of the two states costs a line of code.

AND THE TUBE GREW THIRTY-ONE MORE FIELDS WITHOUT MOVING THE PICTURE

The CRT filter gained a phosphor mask, a parallax model, a per-channel convergence block and a set of visualisation modes. A project that sets only crt_enabled = true today must get exactly the picture it got before them, so every one of those features is off in this const: crt_mask_type 0, crt_mask_strength 0, crt_parallax_strength 0, all six crt_conv_* 0, crt_viz_mode 0, and crt_phosphor_on false. crt_curve_aspect is 1.0, which makes the two-axis barrel equal to the single scalar it replaced.

The fields those switches multiply keep real values rather than zero — crt_mask_triad_px, crt_slot_height_px, crt_eye_dist, crt_glass_ior and crt_mask_boost are divisors, periods or a gain of one, where zero is a divide or a black screen and not a no-op.

crt_phosphor_gui_exempt defaults to 1.0 and is dormant. The default is left where it was because the field is only carried, never read; changing it would rewrite every saved project for no visible effect.

Where one window is on the desktop, in physical pixels.

TWO SPACES, AND THE FACTOR BETWEEN THEM

origin and size are desktop pixels. A window's own egui counts in POINTS, and for one window kind those are not the same length: a Viewport lays the chrome out at a fixed internal resolution and blits up to the window, so one of its points is pixels_per_point desktop pixels. A ToolWindow lays out at its own surface size, where the factor is one.

The dock aims across windows in desktop pixels, so every conversion goes through to_desktop and to_local here. They used to be a bare add and subtract of origin, which is correct only while the factor is one. On a primary window smaller than its render floor the factor is about 0.75, and every drop target, tear-off position and follower chip landed up to a third of the window away from the pointer. The error changed with the window's size, so it changed when the window moved to another monitor.

WHY THE ENGINE HOLDS A FLAG IT CANNOT ACT ON

warp_core has no idea what a debug configuration IS for any given game. For this one it is a hardware tier, a seed, a fixed dt, a skipped tutorial and eight console commands — none of which are engine concepts, and all of which the launch script has been passing as argv to a fresh process.

The hosted game has no argv. It is compiled into the editor, so std::env::args() there belongs to the editor and the game's own flag parsing never sees a --debug. That is the whole reason this is a global rather than a parameter: it is the seam the argv used to come through.

So the bar writes it and the game reads it at the moment it builds a world — the same contract as the three fields above, which the bar writes and the sim loop reads. The engine stays ignorant of what it means.

WHAT IT CANNOT REACH

./run.sh --debug also adds --features sauron_panel to the build. That is a compile-time feature of the binary the editor is ITSELF part of, so no runtime flag can turn it on. The hosted debug boot gets the scenario and the dev flags; it does not get the sauron pane. The launch button in its own window is still the one that does.

#pub static RAW_KEY_WATCH: LazyLock<Mutex<Vec<(&'static str, Vec<RawKey>)>>> = LazyLock::new(|| Mutex::new(Vec::new()))

The keys the app wants on the focus-immune path, one slot per subsystem that asked. Empty by default, so an app that installs no list gets no ring entries at all.

egui consumes a key event whenever any TextEdit holds keyboard focus, and WinitInputHelper then never sees that key. A console whose own text field has focus therefore goes deaf to the key that closes it. The event loop mirrors every watched press into RAW_KEY_PRESSES from the raw WindowEvent arm, before egui gets the event, so one path always survives focus.

The watch list exists to bound the ring. Mirroring every press would let held movement keys and OS key repeat evict a real press within seconds.

ONE LIST, SEVERAL OWNERS

This was a single Vec that every caller replaced wholesale, and a process with two subsystems on the ring silently lost one of them. The editor hosting the game is exactly that process: the game registers its bound keys before the window opens, and the code panel then registered its three punctuation keys from Renderer::new — which ran later and cleared the game's. The backtick was no longer mirrored, so the debug console, whose toggle reads only this ring, could not be opened at all.

The rule the old shape needed — "a host that needs its own keys registers them together with the others" — cannot be honoured across a crate boundary, because neither crate can name the other's keys. So the list is keyed by owner and the effective watch is the union: a subsystem replaces only its own slot, and no registration can delete somebody else's key.
