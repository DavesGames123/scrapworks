The host link is the channel between the SCRAP editor and a game that it launched as a separate process. The hostlink module of warp_core, re-exported by warp_sdk, carries a transport that the editor drives, a surface that the game publishes, and each panel channel. It exists because the editor used to link the game, so a project that did not compile took the tool for fixing it down with it.[1] Every call on the game side costs almost nothing when no editor is listening. The module is native only.

Design

A game with no editor is the normal case

child::attach returns false when the launch flag is absent, and every function in hostlink::child is then a cheap no-op. That is the shipped game. One atomic gates the hot paths, so a game does not lock a mutex to learn "no".[2]

The editor passes SOCKET_FLAG, which is --warp-hostlink, on the command line of the game. The constant lives here, because a writer and a reader of a command line that share no constant drift apart silently.

There is no per-frame message

A frame does not travel on the channel. The game renders into a surface that the editor already holds, so pixels arrive by being written. The channel carries only what changes state: the transport, the size, the focus, and the name of a surface when a resize forces a new one. It is idle while a game runs.[3] Sound crosses the same way, through the name of a shared page.

Every panel that read a global is a message

The transport, the display settings, the profiler and the census were once statics in one address space. Out of process, each broke in the same quiet way: Debug booted the ordinary configuration, a bloom slider moved nothing, and a hierarchy drew its empty state over a full world. None gave an error. The symptom is always that the editor's own copy changed, so a panel looks as if it works.

Messages and the pipe are separate

The wire format is newline-delimited JSON with a reader thread and an inbox drained once a frame. Messages are serde over engine types and name no socket or handle. The two payloads too big for JSON carry a string name. So one protocol sits on two transports: a unix domain socket on macOS and Linux, and loopback TCP on Windows.[4]

The source rejects a named pipe on Windows because a synchronous handle lets a parked read hold off a write from the frame, and fixing that means several hundred lines of unsafe whose failure mode is a hung frame. A loopback port is reachable by each process on the machine, so the address carries a random token after the port, and the host refuses a caller that does not present it. The read of that line is bounded.

Game side

A game calls one function directly. child::report_screen names the screen for the Storyboard, once per frame, and sends only on a change.

hostlink::child::report_screen("deep field");

The rest runs from the engine: child::attach once in run, before any window or GPU work, then child::poll and the pumps once per frame.

Function Purpose

The transport lands in the same static that an in-process editor wrote, so child::poll writes the game's own copy, and no reader downstream changes.

child::visible is true by default. It arms the frame loop, so each way that the message can fail to arrive lands on the old behaviour. A game that renders when nobody looks wastes power, but a game that does not render when somebody looks is a black panel.[5]

The pumps

Each pump re-arms the want of a publisher from what the editor last said, leaves if nobody looks, and sends only when the watched value has a new generation or revision.

Editor side

Host::start listens, and returns nothing when no socket can be made. Host::socket gives the address for the argv of the game. Host::drain returns messages once a frame, and Host::send tells the game something. Host::is_connected says whether a game attached.

Guest is the game's end: Guest::connect, Guest::drain and Guest::send, with Guest::apply_transport to write a received transport to the engine statics.

reap ends the game, the shell that started it, and what that shell left running. On unix this is a process group, and on Windows it is a job object that contain sets up at spawn. A plain kill signals one process, and a script that pipes its output leaves the game running one level down.[6]

Messages

ToGame goes down, with Transport, Step, Resize, Input, Focus, Visible, Scale, Display, Census, CensusInput, Console, Command, Rebind, Profile, Perf, MemoryPressure, Shutdown and others. ToEditor goes up, with Ready, Surface, NoSurface, Audio, Display, Profile, Perf, Census, Console, ConsoleWords, Controls, Screen, Crash and Mem.

CrashReport records a failure with a CrashKind: a panic, a fatal signal, or a stop by the editor to protect memory. The report also goes to a file named for the process, which crash_file_path and read_crash_report handle. MemoryPressureLevel has Warn and Critical. It is a courtesy, because the guarantee that a game cannot take the editor down rests on the editor being able to stop it.

Each message has a stated reason. Transport carries the play state and the debug flag, because the editor once set that flag in a static that the linked game read, and out of process Debug booted the ordinary configuration. Screen is sent on change, a handful of lines per session.[7] Crash carries the panic message, the line and a backtrace from the panic hook, because an exit status tells a person that something broke and nothing about what. A fatal signal cannot send it. Display goes up once as a first look, and the editor owns the settings after that. Going down it is sent on change, so a drag on a slider costs one line per frame while the pointer is down and nothing afterwards.

The surface

The game allocates and publishes, and the editor looks up and imports. The surface must exist before anything renders into it, and the renderer is on the game side. A resize does not free the old surface at once, because the editor is still drawing from it, and freeing it would give a black flash on each splitter drag.[8]

Shared wraps the buffer. On macOS it is an IOSurface, and the handle is a service name and not an integer. The source records that it measured this: the lookup call returns null in a child process, so a mach port crosses through the inherited bootstrap namespace, and the name travels on the JSON channel.[9] The deprecated bootstrap_register call has one call site, so that a migration would touch only those two functions.

The game side has three calls for this.

Function Purpose
child::ensure_surface Allocate and publish when the size changed; idempotent at a given size
child::surface_generation Which allocation is current
child::with_surface Borrow the surface through a closure, behind the session mutex

The generation is a counter and not the surface address, because a pointer freed and reallocated can land on the same address and read as unchanged. child::take_resize is an edge detector over the requested size. The size alone is a level, and a frame loop that resized on it would call the window sixty times a second for ever.[10]

Shared::publish gives the name, Shared::lookup finds a surface by name, and Shared::create allocates. Shared::adopt is a third constructor for a surface that another producer allocated, and it retains the surface, because dropping a Shared releases it and the caller still owns its copy.

hostlink::import turns a surface into a wgpu texture, in texture_from_shared. IMPORT_FORMAT is its format. Both ends use the same call, so they cannot disagree about the format. The unsafe wgpu-hal use is confined to this file.

hostlink::present draws the composed frame into the surface with publish_frame, in one render pass, with no second scene pass or readback. The pass has no aspect correction. It is a copy only because the size now reaches the window, and the source warns that the correctness of this pass depends on a resize two files away.[11]

On the editor side, the texture goes in GameView through GameView::adopt, as gpu describes.

Input

The window of a hosted game is hidden and receives nothing. Each event lands in the editor window, so hostlink::input carries it. InputEvent is the wire type. The editor tap is input::capture and input::drain, and the child side is input::accept and input::replay.

The child replays winit events and not egui events, because the game consumes input twice: its egui context draws menus, and the winit input helper drives everything else. Forwarding egui events would give a game whose menus click and whose camera cannot move. The replay also writes the raw key ring.[12]

A click passes through three coordinate spaces. It starts in physical pixels of the editor window, becomes pixels of the game image, and ends in pixels of the child window. The game image is the space on the wire, because it is the one thing that both ends agree on.[13]

The rules are the ones for a linked game: pointer events inside the published rect, and keys while the panel holds the keyboard and this is the window that it draws in. A drag is exempt from the rect, so an orbit that leaves the panel does not stop. When the key gate shuts under a held key, each forwarded press is paid out as a release, so the game holds no key that nobody presses.[14]

Audio

SharedRings is the same arrangement for the Audio rings: the game allocates, and the name travels on the channel. It uses shm_open and mmap on POSIX and a file mapping on Windows. A game killed with SIGKILL leaves a quarter megabyte named in the namespace until reboot. create unlinks its own name first, so a second run at the same name reclaims the space.[15]

Functions

#pub fn crash_file_path(pid: u32) -> PathBuf

Where a game writes its crash report and the editor reads it.

Named by pid, so the editor — which spawned the child and holds its pid — finds exactly the report it is looking for and not a sibling game's. It shares link_dir with the sockets, which is already the directory both processes agree on.

#pub fn read_crash_report(pid: u32) -> Option<CrashReport>

Read the crash report a game wrote for pid, if it wrote one.

Here rather than in the editor because the parse is serde, and serde_json is a warp_core dependency the editor does not name. The editor reads the report through this so it needs no crate for one call.

#pub fn reap(child: &mut std::process::Child)

End a launched game: the process, the shell that started it, and whatever that shell left running.

THE GROUP AND NOT THE PROCESS, and that is the whole reason this exists. A manifest target with a command key runs a SHELL, and the shell runs the game — ./run.sh builds and then launches, and one of its modes pipes the game into tee instead of execing it. Child::kill signals one pid, so Stop killed the script and left the game rendering into a surface nobody read and printing its frame loop into the editor's terminal. The terminal panel learned this first and states it in the same words.

The caller sends Shutdown before this. The first loop is the chance that message asks for, and it is the only place a game with unsaved state gets one; a game that ignores it costs the Stop frame GRACE_TRIES steps and no more. Then the group is asked, then the group is told.

launch_project puts the child in a group of its OWN. Without that step every signal here would name the editor's group and the editor would be in it, so this function would stop warp.

#pub fn contain(child: &std::process::Child) -> bool

Put a child the editor has just started in a job object, so reap can end the whole tree it grows.

WHY THE SPAWN SITE MUST CALL THIS AND reap CANNOT DO IT ALONE

A process joins a job and every process it starts AFTERWARDS joins with it. Processes it started BEFORE do not. So a job made at Stop time holds the handle and nothing else, and a command target — a shell that launched the game and waits on it — loses exactly the grandchild the unix killpg was written to reach. Call this on the frame the child is spawned.

It still races the child's own first spawn, and std offers no way to close that: CREATE_SUSPENDED needs the thread handle back from CreateProcess, which std::process::Child does not give out. The race is microseconds against a shell that has not been loaded yet, so in practice the job is set before the shell runs a line.

False means no job was made. The caller carries on: reap then falls back to the handle alone, which is what Child::kill always did.

#pub fn apply_transport(&self, msg: &ToGame)

Write a received transport message into the engine's own statics.

This is the whole of what replaces the shared address space. In-process the editor wrote EDITOR_PLAY_STATE and the game's sim loop read it; out of process the editor sends and THIS writes the same static, in the game's own copy of the engine. Every reader downstream is unchanged, which is why the sim loop and the render loop did not have to learn that they are now in a different process.

#pub enum MemoryPressureLevel
/// Free memory is getting low. Give back what can be given back — caches,
/// scratch buffers — and keep running.
Warn,
/// Free memory has crossed the reserve. The editor is about to stop this
/// process. This is the last word before `Shutdown` and a kill: a chance to
/// flush, not a negotiation.
Critical,

How close the machine is to running out of memory, as the editor sees it.

A GAME MAY USE ALL THE MEMORY THERE IS. THIS IS NOT A QUOTA. The editor is the parent, so it is the one process placed to watch the whole machine rather than its own heap alone. It does not budget the game a number. It watches how much memory the MACHINE has left and sends this only when the reserve the editor and the OS need is at risk. So these levels are a courtesy, not a limit: the guarantee that a game cannot take the editor down rests on the editor being able to stop it, not on the game obeying.

#pub enum CrashKind
/// A Rust panic unwound to the top of the game's frame. Message and
/// location are the panic's own; the backtrace is captured in the hook.
Panic,
/// A fatal signal — a segfault, a bus error, an abort. `signal` is the
/// number. Best-effort: a signal handler cannot allocate, so the backtrace
/// may be empty and the message is the signal's name.
Signal { signal: i32 },
/// The editor stopped the game to protect the machine's memory. Not a bug,
/// and the report says so plainly so the panel does not read it as one.
OutOfMemory,
/// A non-zero exit no other kind explains. The editor synthesises this from
/// the status when the game sent nothing.
Exit { code: i32 },

Why a game process ended, when it ended badly.

Four kinds from three producers. Panic and Signal are the game's own, carried by ToEditor::Crash. OutOfMemory is the editor's, set when the editor is the one doing the killing. Exit is the editor's fallback for a non-zero status that arrived with no report to explain it.

#pub struct CrashReport

/// The panic message, the signal's name, or a one-line summary.
pub message: String,
/// Where a panic fired, as `file:line:col`. None for a signal or an exit.
pub location: Option<String>,
/// A formatted backtrace, newest frame first. Empty when none could be
/// captured — a signal handler, or a build with backtraces off.
pub backtrace: String,

pub footprint_bytes: u64,

What a game says on its way out, or what the editor reconstructs when the game could not say anything.

ONE TYPE, TWO PRODUCERS, so the crash surface has one renderer and not two that drift. The game's panic hook fills a rich one — message, location, a backtrace. The editor fills a coarse one from an exit status when no report arrived. A panel that had a private path for each would draw the common case and be wrong on the rare one, which is the case that matters most.

/// force the ask to be re-sent on every frame that had a click in it, or
/// the clicks to be held until the ask changed.
///

#pub fn pump_census()

Forward the census the world just published, when it published one. Once a frame, after the application has rendered.

AFTER, because the publisher builds its rows from a cache that is rebuilt during the frame, and a pump that ran first would forward last frame's world — every position one frame stale, which on a moving body is a row that never quite matches the picture beside it.

WHAT ARMS THE PUBLISHER IS THE FIRST LINE, NOT THE LAST

census_wanted is the publisher's own brake and it is checked before a single row is built. In one process the panel set it directly. Here the panel's ask arrives as a message, is parked in CENSUS_WANT, and is re-asserted from this function on every frame — which is what makes the claim expire the way the channel says it does. Applying it once on receipt would leave a game publishing forever for an editor that had closed the panel, or died with it open.

THE GATE IS THE PUBLISHER'S GENERATION, WHICH IS WHY THIS IS NOT PER-FRAME

The header next door refuses per-frame messages, and a census is the largest thing on this channel — so it is sent when the publisher says there is a new one and not when a frame ends. Stella Nova publishes one frame in six; forwarding on every frame would encode identical rows five times out of six to redraw a panel that cannot tell the difference.

The two ids ride with the rows because they NAME rows in them. inspecting is the publisher's correction for its own renumbering — ids are indices into a table it rebuilds, so the subject moves under the Inspector on every publish — and sending it separately would let it arrive against a census it does not describe.

#pub fn pump_profile()

Carry the frame just closed into the profile window, and send a Report when one is ready. Once a frame, after profile::frame().

Cheap in the shipped game and cheap in a hosted one nobody is profiling: both leave on the first line, and the second costs one relaxed load.

WHY THE GAME REDUCES AND THE EDITOR DOES NOT

The obvious build ships every frame's spans across and windows them on the editor's side, where the panel already windows its own. It is wrong on the only axis this channel cares about: that is sixty JSON encodes a second of a payload that grows with how well the game is instrumented, to produce a picture that is redrawn four times a second. Reducing at the source sends the same reading in one message.

The Report is the same type the editor builds for its own frames, so the two sources reach the panel identically and neither has a private path.

#pub fn pump_perf()

Take this frame's cost and send a quarter second of them at a time. Once a frame, after the render loop has stored its three spans.

WHY THE PANEL COULD NOT JUST READ THE ATOMICS

It did, and that was the bug. RENDER_DRAW_US and the two beside it are process globals filled by whichever render loop is running, so a Performance panel in the editor was reading the EDITOR'S frames — and reporting them under a status line that said the game was running. The panel was not empty and did not error; it drew a healthy sixty at two milliseconds while the game next door did whatever it was doing.

This is the same static, read where it is written. The interval is measured here too rather than sent as a fourth span, because the gap between two calls of this function IS the game's frame period — the same argument the panel makes for timing its own poll, one process over.

AFTER THE FRAME, AND AFTER pump_profile

RENDER_GPU_US is stored when the submission returns, which is the last thing the frame arm does before these pumps run. A sample taken any earlier carries the previous frame's GPU span beside this frame's draw — three numbers from two frames, summed into one column.

#pub fn pump_console()

Keep the console publisher armed, and send the scrollback when it moved. Once a frame, AFTER the game has published — which is after its own frame, because the publisher is part of the game's gui and not of the engine.

THE ARM MUST HAPPEN EVEN THOUGH IT IS A FRAME LATE

devconsole::want_console is what the game's publisher checks first, and nothing in this process was ever going to set it: the panel that used to set it is now in the editor, writing the editor's copy of the static. So a game with a Debug Console open on it did not build a snapshot to send. It built nothing at all, which is why the panel's failure looked like an empty console rather than a stale one.

Arming here rather than in poll costs one frame at the moment a panel is opened and buys the property that the whole console bridge is one function. A frame is nothing against a person reaching for a panel; the want then stays armed for as long as the editor keeps saying so.

WHY THE REVISION IS READ AND NOT THE BUFFER

Most frames print nothing, and on those this is two relaxed loads and a comparison. The buffer is only cloned on the frames the game's own publisher decided something changed, which is what keeps a channel that carries a whole scrollback off the per-frame list this protocol refuses.

#pub fn pump_controls()

Forward the binding table when it has moved. Once a frame.

NO WANT, UNLIKE EVERY PUMP ABOVE IT

The census, the profiler and the console are all gated on somebody looking, because each of them costs the game real work to BUILD — rows off a forty-thousand-entry cache, a span tree, a scrollback clone. A binding table costs a revision load on the frames nothing changed, and on the frames something did it is a hundred short strings. There is nothing here to brake.

Ungated also means the panel is populated the moment it is opened, with no round trip. A want would put an empty Control Map on screen for the frame after a person clicked the tab — which is exactly the state this whole message exists to stop showing.

WHY THE GAME'S REVISION AND NOT THE EDITOR'S ASK

The rebinds arriving on ToGame::Rebind move this counter themselves, so one comparison covers both directions: an edit made in the panel comes back as the table the game actually has, and a rebind the GAME made — its own settings screen, a default that moved in a new build — reaches the panel by the same path with nothing extra to arrange.

#pub fn pump_mem()

Give memory back if the editor asked, and report the footprint. Once a frame, beside the other pumps.

TWO JOBS, BOTH CHEAP WHEN NOTHING IS HAPPENING

The shed runs first and does nothing unless the editor has raised pressure and raised it further than last time — see memcap::shed_if. The report is throttled to a second a sample, because the editor measures this process from outside as well: this figure is the game-attributed meter, not the governor's input, so it does not need frame-rate freshness.

#pub fn requested_size() -> Option<(u32, u32)>

What the editor last asked the game image to be. None before it has asked, which is every frame before the panel has a rect.

#pub fn take_resize() -> Option<(u32, u32)>

The requested size, once, on the frame it changes — for the caller that owns the WINDOW.

WHY THE WINDOW AND NOT JUST THE SURFACE

requested_size above is enough to allocate an IOSurface of the panel's shape, and for a long time that was the whole of the resize path. It is not enough to DRAW at the panel's shape. A hosted game renders at its own window's size — the manifest size, set once at launch and never touched — and present::publish_frame filled the panel-shaped surface with a fullscreen triangle over that image. The sampler stretched it. A panel of any other aspect than the launch window's got a non-uniformly scaled picture, and nothing in the chain said so.

It also meant the game's own layout never learned the panel existed. Its window stayed at the launch size, so every reflow, every anchored HUD element and every available_rect inside the game was computed against a shape the person looking at it could not see.

So the size goes to the window. Everything downstream — the surface config, the render dimensions, the post chain, the game's egui screen rect — is already wired to a window resize and follows for free, and the publish blit becomes 1:1 because the two sizes are finally the same number.

Returns None when nothing changed, so the frame loop pays one atomic load on the overwhelming majority of frames. Marks the size applied on the way out: a caller that drops the value still will not be handed it again, which is correct, because the next real change supersedes it anyway.

#pub fn focused() -> bool

Whether keys are aimed at the Game panel. Always false with no editor, because then nothing else is competing for them.

#pub fn visible() -> bool

Whether anybody is looking at the game image.

True with no editor, because then the window is the picture and the person looking at it is the only opinion there is. The hosted test is first so a shipped game answers on one relaxed atomic load and never reads the flag an editor would have written.

WHAT A FALSE ANSWER IS ALLOWED TO STOP

The publish blit, and the RATE of the frame loop. Not the loop itself: it still drains the channel, still takes a resize, still answers Shutdown, and still renders — a hidden panel raised again must show a picture of the world as it is now, and a loop that had stopped would show the frame it stopped on until it caught up.

It is therefore a throttle and not a switch, and the consequence is worth stating where somebody will find it: a game that runs its world inside its own render call runs that world at the idle rate while its panel is hidden. Warp cannot fix that from here, because render is the one call where the application walks its own world and the engine has no way to separate the two halves of it.

Constants

#pub const IMPORT_FORMAT: wgpu::TextureFormat = wgpu::TextureFormat::Bgra8UnormSrgb

What an imported texture always is.

sRGB, and the SRGB IS THE LOAD-BEARING PART. An IOSurface's pixel format is a byte layout — 'BGRA' — and carries no colour space, so this is a free choice about how the bytes are read. It has to match the pipeline that writes them, and that pipeline is the CRT blit, which is built for the window surface format. On macOS that is Bgra8UnormSrgb.

It was Bgra8Unorm and the mismatch was not a wrong colour. wgpu refuses a render pass whose attachment format differs from the pipeline's, so the game panicked inside the publish blit — the surface handshake completed, the editor imported a texture, and the process died on the first frame it tried to draw. a_launched_process_attaches_and_publishes_a_surface now outlives the publish for exactly this reason. On Windows the free choice is already made: a D3D12 resource carries a typed format, and surface.rs creates it as B8G8R8A8_UNORM_SRGB, which is what wgpu-hal maps this constant to. The two must agree there as well, and there the disagreement is caught — a view in a format the resource cannot be cast to is refused by the runtime.

Take the queue as events the child's own window could have produced, and mirror every key press onto the focus-immune raw ring on the way past.

Empty when nothing arrived, which is most frames — a person is not moving the mouse on most of them.

THE RING IS WRITTEN HERE AND NOWHERE ELSE IN THIS PROCESS

The engine writes the ring from the primary window's WindowEvent arm. A hosted game's window is hidden and produces no window events, so nothing wrote the ring in a launched game at all. Every action that reads the ring AND the input helper lived on its helper half and hid that; an action that reads the ring alone answered nothing. The game's debug console is single-path on the ring on purpose — the two paths double-fired one press against each other — so its key opened nothing under the editor and opened the console in the same game started from a shell.

push_raw_key and not push_raw_key_from: this process has no panels, game_view_embedded is false in it, and capture already applied game_keys_from before the key crossed the socket. A second gate here would be answered by the wrong window.

KEY ROUTING, THE SAME THREE ARMS A REAL EVENT GETS

The window arm in lib.rs decides which of three places a key lands in: a pointer-release key drops the pointer grab, a key under keyboard capture goes to the capture queue, and everything else mirrors onto the raw ring. A hosted game reaches no window arm, so this function is where a hosted game answers the same three questions.

Keyboard capture was the arm that was missing. INPUT_CAPTURED was set by the app, nothing ever wrote CAPTURED_KEYS, and the subsystem holding the keyboard — the game's DOOM framebuffer — drained an empty queue for every key. The same game answered the keyboard when it was started from a shell.

Every key still reaches out, capture or not. That is what the window arm does: it feeds egui before it routes, and capture diverts the RING, not the window's own egui half.
