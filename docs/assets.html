the asset root, path joins and the atlas loader

Assets
CategoryEngine
Modulewarp_sdk::assets
Sourcewarp_core/src/panels/assets/mod.rs
Public items12

Assets is the module of warp_core, re-exported by warp_sdk, that resolves the asset root directory and joins paths under it. It lets an application run from any working directory or distribution layout. All code that uses an asset calls asset_path and does not build a path by hand.[1] The module holds no asset names: which directories exist is application data that arrives through the atlas set descriptor.

Usage

let p = asset_path("resources/iron_ore");
// → "{asset_root}/resources/iron_ore"

warp_sdk states the rule in the doc comment of the re-export: never join a path onto the root by hand.[2]

Resolution order

asset_root checks four candidates in order, then falls back. Each candidate must exist on disk, or the search continues. The result is cached on the first call and does not change for the life of the process.[3]

Step Candidate Layout
1 The STELLA_NOVA_ASSETS environment variable Custom or distribution override
2 src/assets/ relative to the working directory Development, cargo run from the repository root
3 assets/ beside the executable Windows and Linux distributions
4 Resources/assets under the grandparent of the executable A macOS .app bundle
5 src/assets/, unchecked Fallback when nothing exists

The module prints the chosen root and the step that found it.

The environment variable name is fixed in the source of this function. The App manifest format also has env_prefix and resolution_order fields, which the editor and warp_manifest_check read, but asset_root does not read them.[4]

The loader

The loader submodule loads atlases from the descriptor. MegaAtlasSet holds the loaded mega-atlases, one per slot, always MAX_ATLAS_SLOTS long.[5] Its list is private, so each reader goes through MegaAtlasSet::get or MegaAtlasSet::mapping and gets the clamp on the slot number.

load_ship_atlas loads the primary single-directory atlas that the application declared. ship_image_names returns the sorted filename stems of that atlas directory, and an empty list when nothing is declared or the directory is missing. The names are leaked to &'static str.

Interaction with other kits

Each path in the App manifest is relative to the asset root. The Image atlases cache writes under this root, and pak files sit in packed below it.

Functions

#pub fn asset_root() -> &'static Path

Resolve the asset root directory. Cached after first call.

Checks four locations in order, then falls back: 1. STELLA_NOVA_ASSETS environment variable 2. src/assets/ relative to the working directory (dev mode) 3. assets/ alongside the executable 4. Contents/Resources/assets/ inside a macOS .app bundle 5. src/assets/ again, unchecked, when none of the four exist

#pub fn asset_path(relative: &str) -> PathBuf

Types

#pub struct MegaAtlasSet

The loaded mega-atlases, one per slot, always MAX_ATLAS_SLOTS long.

The Vec is private so every reader goes through get or mapping and gets the clamp. Slot numbers are the indices the application gave its atlases in the descriptor.

One placeholder per slot. SharedGpu builds this before the real textures exist, so the first frame has a bind group to draw with.

#pub fn len(&self) -> usize

How many slots this set holds. Always MAX_ATLAS_SLOTS.

#pub fn is_empty(&self) -> bool
#pub fn get(&self, slot: usize) -> &MegaAtlas

Atlas by slot number. Slots past the last one answer with the last one, which is a placeholder in every set that declares fewer atlases than the render path addresses. The clamp keeps a wrong slot number a wrong sprite rather than a panic on the render thread.

#pub fn mapping(&self, slot: usize) -> &TextureMapping

Texture mapping by slot number.

#pub fn mappings(&self) -> Vec<TextureMapping>

Every mapping, in slot order. RenderContext takes the whole list, so the callers that used to build a fixed-size array now call this.
