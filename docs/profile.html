named per-frame spans, the flame chart report, and the Profiler panel

The profiler is the profile module of warp_core, re-exported by warp_sdk, which records a stack of named spans per frame and rolls them into the report behind the Profiler panel. The Performance panel says how much a frame cost, but three phases and a population do not form a call tree, and nothing in the engine named the work. These spans are that naming.[1]

For budgets and warnings, a game normally uses Perf, whose perf::scope opens a profile::Scope of the same name.

Recording

Scope is an RAII guard for one span, and it records nothing unless someone is looking. A guard must be bound to a name, because a binding of _ drops it at once.

let _span = warp_sdk::profile::Scope::new("upload");

Inside warp_core, the scope! macro makes this binding. warp_sdk does not re-export that macro, so a game uses Scope::new or perf::scope.

A span is pushed when it opens, and its end is written when it closes, so the recording is already in pre-order. With a depth on each span, that encodes the whole tree with no pointers. RAII guarantees this: a guard drops at the end of its block, so spans nest strictly.[2]

The guard remembers whether it opened anything. Profiling turns on and off while frames are in flight, and a drop that popped a stack that its constructor never pushed would close another span. A toggle mid-frame therefore costs at most a partial frame.

Interest and the frame

want is the census brake in the same shape. A panel says that it is looking, and the claim runs out after WANT_GRACE frames, which is 3. The clock is frame, which the render loop calls once per frame, so a closed panel stops the instrumentation with no message. This is why a span can stay in a hot path of shipped code: off, it is one relaxed load and a branch.[3]

Function Purpose
want A reader says that it is looking
enabled Whether a scope entered now would record
generation How many frames have closed
frame Close the frame and publish it, once, in the loop
take_frame The last published frame, once
reset Clear the state

Perf reads generation for its own frame clock.

Frame holds its spans in pre-order. Frame::children and Frame::subtree_end walk the tree, Frame::work_ns gives the total, and Frame::self_ns gives the time in a span and not in its callees.

Span holds a static name, a depth, and start and end times in nanoseconds from the start of the frame. MAX_SPANS bounds a scope! inside a loop over many entities.

Threads

Buffers are thread-local, and frame publishes the buffer of the thread that calls it. A worker thread that opens a span records into a buffer that nobody drains, so a recording is capped at MAX_SPANS, 4096, and the overflow is counted. The dropped count is drawn by the panel, because a flame chart that lacks its tail looks like a frame that did less work.[4]

Reports

Window takes frames with Window::accept and produces a Report over WINDOW_MS, which is 250 ms, so four times a second. The panel draws a Report and nothing else, and so does the socket.[5] The local source goes through the wire type too, so a field that stops being filled breaks in front of whoever broke it.

A window, and not the last frame, for two reasons. A flame chart laid out sixty times a second cannot be read, and a span tree at sixty hertz as JSON is the traffic that Host link refuses.

The flame chart keeps one real frame, the most expensive in the window, and never a mean. A mean depicts a frame that did not run.[6] Bar is one span of that frame. Row is one line of the ranked table, which holds at most MAX_ROWS, 96. Report::fps gives the rate, and Window::latest and Window::take_fresh read the result.

The report in full

Report is the unit that the panel draws and the socket carries.

Field Meaning
frames Frames folded into this window
span_ms Wall time that the window covered
worst The most expensive frame, as Bar values in pre-order
worst_ms The instrumented work of that frame
worst_period_ms The wall clock of that frame, gate included
rows Every name seen, most self time first
hidden_rows Rows past MAX_ROWS that were dropped
dropped Spans that the capture could not record

worst_ms and worst_period_ms travel together, because under the budget they differ by the slack that the presentation gate holds, and a panel with only one of them cannot tell a cheap frame from a late one.[7]

Row totals one name over the window.

Field Meaning
name The span name
calls Entries across the whole window, not per frame
self_ns Time with the children taken out
total_ns Time with everything it called
max_ns The most expensive single entry

Bar holds a name, a depth, and start and end times in nanoseconds from the start of its frame. Report::children and Report::subtree_end walk the bars in the same pre-order as Frame.

The panel

ProfilerState holds the panel state, and draw paints a flame chart of the worst frame with a table below that ranks each span by self time. Source chooses the editor or the game, because these are different processes, and a chart that did not say so would be read as the game's whatever it was.[8]

Across processes

The game keeps its own Window, and pump_profile in hostlink::child sends one Report per window while the editor wants one. The Profile message from the editor re-arms the want, and the expiry stays with want, counted in frames.

Limitations

There is no second timeline per thread. The source calls that the obvious next version, and a panel change as much as a capture change. The panel code compiles on native targets only, and the span engine also compiles on wasm.

The Perf Monitor panel reads the timings of the render loop, so a game that records no spans still gets those.

#pub fn want(on: bool)

Say that something is reading. Call it every frame a reader is open.

false gives up at once. Not calling it at all gives up within WANT_GRACE frames, which is the path that carries the weight — a panel that was closed, or an editor that exited, says nothing at all.

#pub fn enabled() -> bool

Whether a scope entered right now would record anything.

#pub fn generation() -> u64

Frames closed since the process started.

#pub fn frame()

Close the frame on this thread, publish it, and start the next.

Call once per frame from the loop, whether or not anything is reading. It is the clock want expires against, so a loop that only called it while a panel was open would leave the gate stuck at whatever it last was.

Spans still open here are closed at this instant and counted. That is a caller putting frame() inside something it also timed, and the choice is between a well-formed tree with one span longer than it should be and a tree with a hole in it. The first can be read.

#pub fn take_frame() -> Option<Frame>

The frame frame() last published, taken out of the slot.

None when nothing has been published since the last call, which is the normal answer for a reader polling faster than the loop runs.

#pub fn reset()

Drop the recording in progress and anything published. For tests, and for a reader that wants to be sure the next frame it sees began after a Clear.

The direct children of the span at i.

#pub fn subtree_end(&self, i: usize) -> usize

One past the last span of the subtree rooted at i.

#pub fn work_ns(&self) -> u32

The instrumented work of the frame: every top-level span added up.

NOT total_ns, and the difference decides which frame a window keeps. total_ns is the PERIOD — the wall clock from one frame() to the next — and the Performance panel next door spends a section header on why that is a different quantity: submissions are gated at the frame budget, so the period bottoms out there however cheap the frame was.

Ranking by period therefore picks the frame that WAITED longest, which is usually the one that did least. Worse, the first frame after profiling is turned on has a period stretching back to whenever the loop last called frame() and contains no spans at all, so it wins its window outright and the flame chart is empty with a large number over it. Work is zero for that frame, which is the right answer.

#pub fn self_ns(&self, i: usize) -> u32

What the span at i cost with its children's time taken out.

The number a profiler is actually read for. Total time on a span near the root is the frame restated — it is large because everything is inside it, not because anything in it is slow.

Constants

#pub const MAX_SPANS: usize = 4096

Spans one thread will record in one frame before it stops recording.

Four thousand is far past what an instrumented frame loop produces and far short of what would cost memory worth thinking about. It is here for the unbounded case — a scope! inside a loop over ten thousand entities, or a worker thread whose buffer nothing drains — where the alternative is a Vec that grows until the process dies.

#pub const WANT_GRACE: u64 = 3

How many frames a reader's interest outlives its last want(true).

The census's constant and the census's reason: a reader that stops asking gives up within a few frames rather than at once, so interest survives a frame where the panel did not happen to draw.

#pub const WINDOW_MS: f32 = 250.0

How long a window covers before it becomes a Report, in milliseconds.

Four a second. Slow enough that the picture holds still to be read, fast enough that a change made in the game shows up while the person who made it is still looking at the panel.

#pub const MAX_ROWS: usize = 96
