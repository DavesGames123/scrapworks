Bindings is the table between a physical input and a game verb. The bindings module of warp_core, re-exported by warp_sdk, lets an application declare its actions once, after which what a key does, what it did by default, what the Control Map panel paints and what a rebind writes are all questions about this one table.[1]

Design

Before this table, a control scheme was two hardcodings kept in step by hand: a const table of keycaps for a settings screen, and a pass of key checks for behaviour. Nothing sat between the key and the verb, so a remap had nothing to write to. Now physical layout stays as data, and which action sits on which key is a lookup. The panel draws the table and the input pass reads it, so the two cannot disagree.

Usage

Declare a 'static catalog, register it in new, and read verbs by id.

static ACTIONS: &[bindings::Action] = &[
    bindings::Action::new("p1_up", "Left Up", "Play", &[bindings::Chord::key(RawKey::W)]),
    bindings::Action::new("p1_down", "Left Down", "Play", &[bindings::Chord::key(RawKey::S)]),
];

bindings::register(ACTIONS);

if bindings::held("p1_up", input) {
    // ...
}

bindings::held asks whether a verb is down, bindings::pressed whether it went down this frame, and bindings::released whether it came up. ActionId is the trait that these functions take as an id.

bindings::register replaces the catalog and loads stored overrides. Overrides for actions not in the catalog are kept and written back, so a build with a smaller catalog does not erase bindings that it cannot see.[2]

Actions

Action is copyable, because each field is 'static.

Field Meaning
id Stable name that the store writes; renaming it orphans an override
name What the panel calls it
group The section, and the colour class of its keycap
context When the action can fire; empty means always
hint One line under the name
defaults The chords at the start

Two actions in different contexts may share a chord without a conflict. A real scheme has W as pan and W as thrust. The engine takes the word of the application: bindings::held and bindings::pressed do not consult the context, because the application gates those calls already.

Chords

Chord is one physical input plus the modifiers held with it, and it is a plain value. Input carries mouse buttons and wheel directions beside keys, so the mouse diagram in the panel holds real bind targets. MouseZone lists Left, Right, Middle, Back, Forward, WheelUp and WheelDown.

A chord comes from Chord::key, Chord::keyed, Chord::mouse or Chord::moused. parse_chord reads the text form. One table of keys carries the token and the label for each key, so names stay in one list.

Matching

Modifiers match by subset: a chord is satisfied when each modifier that it names is down, whether or not others are. Shift+W therefore still pans when W is bound plain.

When two actions are satisfied on one input, the action that names more modifiers wins and the others are suppressed. With 1 and Ctrl+1 both bound and Ctrl down, only Ctrl+1 fires. That one rule replaces a hand-written suppression flag.[3]

Reading the table

Function Purpose
catalog Each action, in declaration order
groups The groups in the catalog, in first-seen order
action One action by id
actions_on Everything bound to one physical input
bound_keys Each key that any action names
revision Moves when the table changes

bindings::held, bindings::pressed and bindings::released all apply the specificity rule. They take the WinitInputHelper that the application receives.

Rebinding

set rebinds an action and writes the store. An empty list is a deliberate unbind, not a reset. reset and reset_all restore defaults. chords gives what is bound now, defaults what was bound at the start, and is_default whether they agree.

Only overrides are stored. chords falls through to the action's defaults when nothing overrides them, so a later build can move a default and reach everyone who never touched that action.

Conflicts

Two actions on an identical chord are a conflict. conflicts names them so that the panel can paint both red, and is_conflicted tests one. The rebind is still accepted, because refusing it would make it impossible to swap two keys without a parking key.[4] Two actions on one key with different modifiers are not a conflict.

The store

bindings::store reads and writes a flat file through the per-person config directory, one action per line:

# comment
camera.pan_up   = W, Up
ui.station      = Ctrl+E
combat.hold     =

The format is not TOML, because the content is a flat map and hand-editing is common. An empty right side records a deliberate unbind. A line that does not parse is dropped, so a file from a later build costs that one binding and never the run.[5]

Across processes

The table is process-local, and the game is not always this process. The process that declared the table owns it: it keeps the store, applies each rebind, and publishes a Snapshot when revision moves. The process that draws it is a viewer. A viewer calls install, never writes the file, and queues a rebind as an Edit for the owner to perform and echo back. Two processes that wrote one file would each write the half that they could see.[6]

Function Purpose
install Draw another process's table; turns on viewing
detach_viewer The game is gone; restores what was shelved
is_viewing Whether this process owns what it draws
drain_edits Rebinds made here, for the owner
apply_edit Perform one, on the owning side

Host link carries these in pump_controls.

Interaction with other kits

bound_keys returns every key that any action names, for set_raw_key_watch, so the focus-immune path in Types follows a rebind. live_mods reads the held modifiers. Each bindings::held and bindings::pressed call takes the table lock. At a few dozen calls a frame this costs microseconds, and a rebind lands on the very next query.

Only actions this build knows about are cleared. An override belonging to a catalog this process does not carry is left alone, for the same reason register keeps it: a tool window must not be able to wipe the game's bindings by pressing Reset on a panel that lists none of them.

#pub fn revision() -> u64

Bumped by anything that changes the catalog or the overrides.

What a publisher compares against what it last sent. It is compared for equality only: a viewer's copy is somebody else's counter and interpreting it as an ordering would be reading meaning into a number minted elsewhere.

#pub fn is_viewing() -> bool

Whether this process is drawing a table it did not declare.

#pub fn snapshot() -> Snapshot

The whole table, in a form that can go on a socket.

#pub fn install(snap: Snapshot)

Draw somebody else's table.

Replaces whatever is here and turns on viewing, which is what stops the mutators writing a store this process does not own. Idempotent: the owner republishes on every change of its own revision, and installing the same snapshot twice leaves the same table.

#pub fn detach_viewer()

The game whose table this was is gone.

Puts back whatever this process had declared for itself, which for a build that hosts and does not link is nothing — the panel goes back to its empty state, correctly, because there is again no application to have controls.

The outbox is dropped rather than held. An edit queued for a process that has exited has nowhere to go, and delivering it to the NEXT game would apply a rebind aimed at a catalog that game may not have.

#pub fn drain_edits() -> Vec<Edit>

Rebinds made here, for whoever owns the table. Empties the queue.

#pub fn apply_edit(e: Edit)

Perform one, on the side that owns the table.

Routed through the ordinary mutators, so an edit that arrived over a socket takes the same path as one made in this process: it lands in the table and it lands in the store. There is nothing here that knows it came from elsewhere, which is what keeps the two paths from diverging.

#pub fn actions_on(input: Input) -> Vec<(Action, Chord)>

Every action bound to one physical input, with the chord that does it.

The panel colours a keycap from this: no entries is unbound, one entry takes that action's group colour, more than one is a stack.

#pub fn conflicts() -> Vec<(Chord, Vec<Action>)>

Chords carrying more than one action that can fire at the same time.

Identical chords only. Two actions on one key with different modifiers are resolved by specificity and are not listed here, and two in different contexts are not a conflict at all.

#pub fn is_conflicted(c: Chord) -> bool

True when this exact chord carries more than one action in one context.

#pub fn bound_keys() -> Vec<RawKey>

Every key any action is bound to.

For set_raw_key_watch, so the focus-immune press path follows a rebind instead of watching whatever the application hardcoded at startup.

#pub fn live_mods(input: &WinitInputHelper) -> Mods

The modifiers down right now.

Command and the Windows key are one bit. An application binding Logo+S gets Cmd+S on a Mac and Win+S elsewhere from one declaration, which is what the author of that binding meant.

#pub struct Action
/// The name the store writes and the code names. Dotted, stable, never
/// shown to a person. Renaming one silently orphans anybody's override of
/// it, which is the cost of it being the identity.
pub id: &'static str,
/// What the panel calls it.
pub name: &'static str,
/// The section it is listed under, and the colour class of its keycap.
pub group: &'static str,
/// When this action can fire at all. Empty means always.
/// 
/// Two actions in different contexts may share a chord without it being a
/// conflict. That is not a nicety: a real scheme has W panning the camera
/// and W being thrust while piloting, and those are two actions on one key
/// on purpose. Without this field the panel would open reporting the
/// scheme's own defaults as broken, which teaches people to ignore the
/// conflict marker — and then it is worth nothing when a conflict is real.
/// 
/// The engine takes the application's word for it. `held` and `pressed` do
/// not consult this; the application already gates those call sites, and a
/// context the engine enforced would be a second, disagreeing copy of that
/// gate. This says only "these two are never live at once".
pub context: &'static str,
/// One line under the name, when there is something worth saying.
pub hint: &'static str,
/// What it is bound to before anybody changes anything.
pub defaults: &'static [Chord],

One thing a person can do, and what it is on by default.

Every field is 'static: an action catalog is written down in the source of the application, not built at run time. That is what keeps Action Copy and the whole table cheap to hand around.

#pub struct ActionWire
pub id: String,
pub name: String,
pub group: String,
pub context: String,
pub hint: String,
pub defaults: Vec<Chord>,

One action, with its text owned rather than 'static.

Action is Copy because a catalog is source code, and that is worth keeping — every query in this file copies one. It is also exactly what stops an Action being deserialised, because there is no &'static str on the far end of a socket. So the wire carries this and install puts the 'static back by interning.

#pub struct Snapshot
pub actions: Vec<ActionWire>,
/// Sorted by id, so a snapshot resent for an unrelated reason is the same
/// bytes as the last one and a diff of the channel means something.
pub overrides: Vec<(String, Vec<Chord>)>,

A whole binding table as the process that owns it sees it.

The overrides ride with the catalog and are not left to the viewer's own store. Both processes read the same file, but only one of them has the catalog that says which lines in it are live — a viewer loading the file itself would be guessing at a table it cannot see, and would disagree with the owner the moment the owner wrote to it.

#pub enum Edit
Set { id: String, chords: Vec<Chord> },
Reset { id: String },
ResetAll,

A rebind made in a process that does not own the table.

Three variants and not one, because reset is not set to the defaults: it REMOVES the override, so a later build that moves a default reaches somebody who pressed Reset. Collapsing them here would quietly convert every reset into a pin at whatever the default was on the day.

#pub trait ActionId

Anything that names an action.

Implemented for the string types so a caller can pass an id directly, and meant to be implemented by an application's own action enum so the call sites read as held(A::CameraUp, input) and a typo is a compile error rather than a control that silently does nothing.

The return is &str and not &'static str on purpose. A panel editing this table holds the id it is working on as a String — it came from a click, not from source — and a 'static return would force that caller to leak it to say the same thing.
