Project settings

ArticleReference

From Warp Wiki, the reference for the Warp engine SDK

the registry of [settings.*] blocks that keep a project's look in its manifest

Project settings
CategoryEngine
Modulewarp_sdk::project_settings
Sourcewarp_core/src/project_settings.rs
Public items9

Project settings is the registry of named settings blocks that live in warp_app.toml under one [settings] table. It is the project_settings module of warp_core, re-exported by warp_sdk. Each subsystem registers a Section, a name with a way to install a table into its global and a way to write that global back. The module owns the file format and the diffing, and a subsystem owns neither.[1]

Design

DisplaySettings is a process global, and once nothing wrote it down. A person could tune a CRT for an hour, close the editor, and get the flat default back. A project that wanted a look had one place to put it: hand-written Rust in its own main.rs.[2]

The App manifest carries deny_unknown_fields, so a section that is not a declared field fails to parse and takes the whole project with it. A field per section would put every future section in the manifest code. So the manifest declares one field, settings, as a free table, and each section is a sub-table of it. The manifest never learns a section name, and a new section is one register call.

The namespace separates two questions. [app], [assets] and [build] say what the project is, and a build reads them. [settings.*] says how it looks, and a frame reads them.

Sections

SETTINGS_TABLE is the manifest key, "settings". A Section is a plain value with three fields:

Field Meaning
name The sub-table name. "display" becomes [settings.display].
load Install a table into the global of the subsystem.
save Merge the live values into a table that is already created.

The load function gets nothing when the project names no such table. The subsystem must then install its default, because otherwise one project's look would leak into the next.[3] These are function pointers and not closures, so a section costs no allocation. Neither takes state, because a section works on the global that a frame already reads.

The engine has two built-in sections:

Block Owner Holds
[settings.display] The viewport Post chain, CRT tube, depth of field, anti-aliasing
[settings.theme] The Palette roles The game palette, on native targets

ensure_builtins seeds these at the first touch, from every entry point of the module. An init function would be one more thing that an application could forget, and the failure would be silent. So registration has no order to get wrong.[4]

Usage

An application adds a section with register, at any time. A second call with the same name replaces the first, so two writers never share one table.

read and merge are what a section normally calls. This is the theme section from the palette module, trimmed:[5]

pub fn section() -> crate::project_settings::Section {
    crate::project_settings::Section {
        name: "theme",
        load: |table| set_palette(crate::project_settings::read(table)),
        save: |into| crate::project_settings::merge(into, &palette(), &Palette::DEFAULT),
    }
}

Reading

load_all installs each section from a manifest table. run calls it through a boot step, before the window and GPU exist, so a built artifact boots with the look that it was tuned with. reset_all installs each default, which is the engine state that a closed project should leave.

read deserialises one table, or gives the default when there is none. A table that does not deserialise also gives the default, with no message. The alternative is refusing to open a project over a typo, and the source judges that a look is not worth it. The value is visibly wrong on screen, which is the report. The type must treat each missing field as its default, through #[serde(default)], because the table holds only the keys that differ.[6]

load_all, reset_all and save_all must run outside Renderer::gui. A debug_assert guards this, because a call while a frame holds the display settings otherwise deadlocks with no panic or log.[7]

Writing

Only what differs is written. merge serialises the live value and the default, compares key by key, writes the keys that differ, and removes the keys that have gone back to default. The table is therefore exactly the choices of the project, and a fresh project has no [settings] table. Without the removal, a slider dragged away and back would leave a key that says nothing.[8]

save_all merges each registered section into a toml_edit document. It creates the table on demand and removes it when every section comes out empty, so a project that tuned nothing has no first-save diff. The [settings] root is implicit, so a reader sees only [settings.display].

fingerprint returns what save_all would write, as text. The editor compares it to the last one to find whether a slider moved. It is defined as the save and not beside it, so it cannot say "unchanged" about a value that a save would write.

Unknown keys survive. merge touches only keys that it can name, and save_all walks only registered sections, so an older engine that opens a project tuned by a newer one preserves the settings that it cannot read.[9]

Who reads the file

The editor writes the block on save. Its panels change the live viewport during a drag, because a write per drag step would rewrite the manifest sixty times a second. Both processes read the same file. A shipped game reads it in run, and the editor reads it when the project opens and pushes changes to a hosted game over the socket.

Limitations

Comments inside a [settings.*] table may not survive a rewrite of their key. Comments elsewhere in the file survive, because the editor holds the document in toml_edit and this module touches one table.

warp_sdk::project_settings

Functions

#pub fn register(section: Section)

Add a section, replacing any section already registered under its name.

Replacing and not pushing: an application that registers twice — two windows, a satellite, a test that runs after another test — would otherwise get two writers of one table, and which of them won would depend on registration order.

#pub fn load_all(settings: Option<&toml::Table>)
#pub fn reset_all()

Install every registered section's default.

Closing a project is not the same as opening one with no settings, but the engine state it should leave behind is identical.

#pub fn save_all(doc: &mut toml_edit::Document)

Merge every registered section into a document's [settings] table.

Creates the table on demand and REMOVES it again when every section came out empty, so a project that has tuned nothing keeps a manifest with no [settings] in it at all. An empty table left behind would be a diff on the first save of every project that never touched a slider.

#pub fn fingerprint() -> String

What save_all would write right now, as text.

The editor compares this against the last one it saw to decide whether a slider has moved. It is deliberately defined AS the save rather than beside it: a fingerprint computed some other way could say "unchanged" about a value that a save would write, and the person would lose the edit at the one moment they were told there was nothing to lose.

Equal strings therefore mean equal files, and the comparison is exact rather than a hash — there is no collision to reason about, and the string is a few hundred bytes at most because only non-default keys are in it.

#pub fn read<T: serde::de::DeserializeOwned + Default>(table: Option<&toml::Value>) -> T

Deserialise one section's table, or its default when there is none.

A table that does not deserialise gives the default too, and says nothing. The alternative is refusing to open a project over a settings key somebody hand-edited into a typo, and a look is not worth a project that will not open. The value is visibly wrong on screen, which is the report.

T must treat every missing field as its default — #[serde(default)] on the struct — because the table on disk holds ONLY the keys that differ.

#pub fn merge<T: serde::Serialize + PartialEq>(into: &mut toml_edit::Table, value: &T, default: &T)

Write the keys of value that differ from default, and remove the rest.

One implementation serves every field of every section, which is what the registry is for: eighty-four display fields need no per-field code, and the next section needs none either.

The removal half is as load-bearing as the writing half. Without it a slider dragged away from its default and back would leave the value behind in the file, and the project would carry a key that says nothing forever.

Types

#pub struct Section
/// The sub-table name. `"display"` becomes `[settings.display]`.
pub name: &'static str,
/// Install a table into the subsystem's global.
/// 
/// `None` means the project named no such table, and the subsystem must
/// install its DEFAULT rather than keep what the last project left. A
/// section that skipped that would leak one project's look into the next.
pub load: fn(Option<&toml::Value>),
/// Merge the subsystem's live values into its own table.
/// 
/// The table is handed over already created. `merge` is what almost every
/// implementation should call, and it is what decides that a value equal
/// to the default is a key that should not exist.
pub save: fn(&mut toml_edit::Table),

One subsystem's settings block.

Function pointers and not closures, so a Section is a plain value that costs no allocation and can be built in a const. Neither pointer takes the subsystem's state as an argument: a section reads and writes its own global, because that global is what a frame already reads.
